# Solo SDD: алгоритм

Разработка через спецификации для одного владельца и двух агентов, Claude Code и Codex. Владелец ставит цель и принимает результат. Агенты ведут работу сами: от плана до кода, смёрдженного в main, без вопросов по ходу. В основе OpenSpec со схемой `solo`, поверх него работают скиллы из `skills/`.

Как устроен репозиторий и как его раскладывать, написано в [README.md](README.md). Откуда взята каждая часть, — в [SOURCES.md](SOURCES.md). Почему правила сформулированы именно так, — в [LESSONS.md](LESSONS.md).

## Принципы

1. **Спецификация — источник истины.** Поведение меняется вместе со спекой, в одном change. Код, который расходится со спекой, считается дефектом, даже если тесты зелёные.
2. **Маленький change.** Один результат, который владелец может проверить сам, одна область кода, не больше 10 задач. Если выходит больше, это несколько change, связанных через `Depends On`.
3. **Свойство, а не способ.** Спека говорит, что должно быть верно («история git не меняется»), а не как это проверить («искать подстроку push»). Способ выбирает исполнитель.
4. **Доказательство, а не отчёт.** Готовность подтверждают наблюдения: тест, который падает на прежнем коде, и живой сценарий там, что видит человек. Зелёные тесты, отчёт исполнителя, «функция вызвана» доказательствами не считаются.
5. **Без вопросов по ходу.** Неясность агент решает сам и записывает решение. Спрашивать можно только перед тремя вещами: платный вызов, удаление или перезапись данных, действие на проде. В вопросе называется, что произойдёт, сколько вызовов и какая сумма.
6. **Блокер не останавливает работу.** Сначала ищется обход: моки, старые данные, `.env`, соседний сервис. Нет обхода — непроверенное записывается в `verification.md` и `docs/waiting.md`, остальное закрывается.
7. **Одна задача — один исполнитель.** Ведущий агент планирует, пишет спеки исполнителям и принимает результат своими командами. Код он не пишет. Ревью делает агент, который этот код не писал.
8. **Ничего не выдумывается.** Значения, которые знает источник (CLI, API, база), спрашиваются у источника. Честное «не смогли определить» лучше правдоподобного значения.
9. **Дёшево.** Тесты, приёмка и эксперименты идут на самых дешёвых моделях. Тяжёлое чтение уходит исполнителям, чтобы контекст ведущего не сжимался.
10. **«Готово» = в архиве, проверено вживую, смёрджено.** Если чего-то из трёх нет, статус «не готово» с указанием, чего не хватает.

## Цикл

```
 0 project-init ─► 1 context-resume ─► 2 evidence-research / model-council (по необходимости)
                                                   │
 9 spec-audit ◄─ 8 ship ◄─ 7 закрытие ◄─ 6 доказательство ◄─ 5 spec-next ◄─ 4 spec-analyze ◄─ 3 spec-plan
 (каждые 5 архивов)                                   ▲
                                         debug-profile, ui-check, agent-quality
```

Сквозные скиллы на любом этапе: `work-status` (пять строк о состоянии), `context-resume` (после паузы, сжатия контекста или смены агента).

### 0. Проект готов к агентам — `project-init`

Один раз на проект. Создаются `AGENTS.md` (правила проекта: команды, карта, границы и инварианты, проверка), `CLAUDE.md` со строкой `@AGENTS.md`, `openspec/config.yaml` со схемой `solo` и «Замыслом» (шаблон — `templates/openspec/config.yaml`), `.env.example`, README.

**Ворота G0:** `openspec validate --all --strict` проходит; каждая команда из таблицы `AGENTS.md` реально запускается; проект поднимается по README в чистой оболочке.

### 1. Контекст — `context-resume`

При возврате к проекту, после сжатия контекста или при смене агента. Читаются правила проекта, `handoff.md`, `verification.md` открытых change, `git status` и история по словам задачи. На выходе карта: цель, источник истины, последнее подтверждённое состояние, решения владельца, блокеры, следующий шаг. Факт из истории сверяется с файлами и сервисом. Если они расходятся, верным считается текущее состояние.

### 2. Исследование и решение — `evidence-research`, `model-council`

Только когда без этого план не написать: выбор технологии, сервиса или подхода. `evidence-research` даёт таблицу вариантов по ограничениям владельца, каждый факт — с источником и датой. `model-council` собирает обсуждение нескольких моделей до согласия, если решение спорное. Перед запуском всегда называются состав, лимит кругов и верхняя граница вызовов. Итог идёт в `spec-plan` как вход.

### 3. План — `spec-plan`

Вход: план, список багов, итог обсуждения. Выход: очередь маленьких change. Код не пишется.

- Единица годится, если у неё один проверяемый результат, одна область кода, не больше 10 задач и есть сценарий живой проверки. Баги группируются по общей причине, а не «один баг — один change».
- Единица, которая уводит от «Замысла» из конфига, в change не превращается и выносится в отчёт.
- Артефакты строятся по порядку схемы: proposal → specs → verification → tasks (см. «Артефакты change»).
- Что ждёт человека, доступа или платного согласия, задачей не становится. Это `Needs` в `verification.md`. Change, целиком состоящий из таких условий, получает файл `WAITING`.
- Каждый пункт входа сопоставлен с change. Пункт без change считается ошибкой.
- Баг с найденной причиной идёт коротким треком (раздел «Багфикс» в `spec-plan`): воспроизведение и место причины в proposal, сценарий бага добавляется в спеку, первая задача — падающий тест на этот сценарий, не больше 5 задач, попутные правки в Out of Scope. Причина не найдена — сначала `debug-profile`.
- UI-change начинает What Changes строкой Design Read по `DESIGN.md` (нет строки `Dial` с тремя числами — дайлы 1/1/1 и «черновик без направления»); Live Scenario — списком «элемент → действие → результат»; данные владельца — заглушки `[нужны данные: …]`.

**Ворота G1:** `openspec validate --all --strict`; затем `spec-analyze` по каждому созданному change (этап 4); покрытие входа полное.

После G1 папки созданных и изменённых change уходят одним коммитом `change: <id>, …`, без чужих правок. Если `openspec/changes` игнорируется, коммита нет, а отчёт пишет «план вне git».

### 4. Сверка до кода — `spec-analyze`

Перед первой задачей каждого change. Проверяется спека сама с собой, пока кода нет: дыра в `tasks.md` стоит одной строки, а после реализации — переделки.

Проходы:

| № | Проход | Что ищет |
|---|---|---|
| 1 | Покрытие | Требование или сценарий без задачи и теста; задача без требования |
| 2 | Рамки solo | Пустой Out of Scope; незаархивированный Depends On; пересказ вместо цитаты в Source; больше 10 задач; ожидание человека в задачах; Live Scenario, который не доходит до того, что видит владелец |
| 3 | Проверяемость | Задача без наблюдаемого критерия |
| 3a | Исполняемые свойства | Инвариант, round-trip или идемпотентность, проверенные только примерами |
| 4 | Потребитель | Новое поле, модуль или значение, которое никто не читает |
| 5 | Неясности | Пустые, ошибочные и частичные случаи; «нет данных» против «не прочитали»; повтор; что видит владелец в каждом исходе; дрейф терминов; `TBD` |
| 6 | Формулировки | Способ вместо свойства; номера строк вместо структуры; зашитые значения; слова без меры |
| 7 | Согласованность | Противоречие основной спеке; решение в design без задачи; задача использует то, что появится позже; уход от замысла |
| 7a | Совместимость требований | Требования, верные по отдельности и невыполнимые вместе; несовместимые ограничения; неописанное сочетание условий; скрытое допущение |

Проверки, выведенные из дефектов конкретного проекта, лежат в его `openspec/analyze.md` (шаблон — `templates/openspec/analyze.md`). Скилл их подхватывает сам.

Находки CRITICAL и HIGH агент исправляет в артефактах, а решения пишет в `Decisions Without Owner`. Код в этом проходе не меняется.

**Ворота G2:** нет открытых CRITICAL и HIGH; всё из `Depends On` в архиве. Иначе change не готов, и `spec-next` берёт другой.

### 5. Реализация — `spec-next`

За один запуск закрывается один change, от выбора до архива.

1. Шаг 0: `python3 ~/.local/bin/openspec-after-update.py`. Скрипт раскладывает скиллы и правила из этого репозитория, а после обновления OpenSpec пересобирает схему `solo`.
2. Выбор: названный change; иначе тот, где сделано больше всего; иначе следующий с закрытыми зависимостями. Change с файлом `CLAIM` (взят другим агентом) или `WAITING` пропускается.
3. Захват: `openspec/changes/<id>/CLAIM` в основной папке проекта со строкой `<агент> <дата>`; у Claude ещё `session=<id сессии>` (`$CLAUDE_CODE_SESSION_ID`), по нему хук записи узнаёт свой `CLAIM`. Сам хук ставит метку только при правке `tasks.md`, которая отмечает новую задачу: анализ и аудит, правящие артефакты, change не занимают.
4. Сверка: `spec-analyze` (этап 4).
5. Задачи из `tasks.md`. Если затронуто больше одной области кода, ведущий агент оркестрирует и сам не пишет:
   - Claude — `codex-orchestration` (исполнители Codex CLI) или `opus-sonnet-orchestration` (субагенты Sonnet);
   - Codex — собственные субагенты.

   Правила оркестрации:
   - Разбиение по владению файлами. Независимые юниты идут параллельной волной, юниты на один файл — в разные волны или в отдельные worktree.
   - У юнита одно доказательство, максимум два-три. Если больше, юнит делится.
   - Спека исполнителю начинается с шапки «выполни сам, не спрашивай» и содержит свои и чужие файлы, образец, все литеральные значения, запрет коммитов и формат отчёта.
   - Приёмка своими командами и `git status` своего дерева. Отчёт исполнителя остаётся утверждением, а не доказательством.
   - После параллельной волны проводится ревью общего диффа.
6. Задача отмечается `- [x]` только после её собственной проверки.
7. Независимая приёмка: ревьюер с чистым контекстом на самой дешёвой модели получает только delta-спеки, Live Scenario и дифф, без отчётов исполнителей и `Result`. По каждому требованию — выполнено, частично или нет, с местом в коде и тестом; отдельно — правки, которых не требует спека. «Нет» — доработка и одна повторная приёмка, затем `Not Verified`.

Несколько готовых change сразу (только Claude Code) — `spec-dispatch`: главная сессия на Sonnet раздаёт их волнами Opus-оркестраторам, по одному на change в своём worktree во временной папке. Оркестратор ведёт change по `spec-next` в режиме «Под диспетчером»: сам при трёх задачах и меньше в одной области кода, иначе через исполнителей; не мёрджит и сдаёт блок статуса вместо отчёта. Диспетчер кода не читает: повторяет команды из статуса, мёрджит по одному, конфликт не чинит, поставляет main.

### 6. Доказательство

| Что меняется | Чем доказывается |
|---|---|
| Любое поведение | Тест, который падает на прежнем коде. Проверка формы («поле существует») не засчитывается |
| Инвариант, round-trip, идемпотентность | Property-based тест (`fast-check`, `Hypothesis`), названный по Requirement. Тест должен падать хотя бы на одной мутации кода, генератор — доходить до граничных состояний |
| То, что видит человек | `Live Scenario` из `verification.md` на собранном артефакте или стенде |
| Интерфейс | `ui-check`: снимки 1280 и 390, обе темы, клик по каждому изменённому элементу |
| Качество AI-агента | `agent-quality`: A против B на одном размеченном наборе, одно изменение за прогон |
| Сбой в работающем сервисе | `debug-profile`: воспроизведение → версия и среда → локализация по логам → одна гипотеза. После двух неудачных правок — стоп и разбор |

Тесты и приёмка идут на самых дешёвых моделях. Платный прогон запускается только с согласия, с числом вызовов и суммой.

### 7. Закрытие

- В `verification.md` заполняются `Result` (что запущено и что получено, с датой), `Not Verified` (что не доказано и почему) и `Decisions Without Owner`.
- `openspec validate <id> --strict --no-interactive`, затем `openspec archive <id> --yes`: архив сам синхронизирует основные спеки. Потом `openspec validate --all --strict`.
- Если обязательный живой сценарий не прошёл и разрешённого Fallback нет, архив не выполняется, статус «не готово».
- Внешний остаток после архива допустим, только если его прямо разрешают правила проекта или владелец. Основание пишется в `verification.md` и `docs/waiting.md`, отчёт различает «архивирован» и «внешняя приёмка не готова».
- Файл `CLAIM` удаляется.

**Ворота G5:** `verification.md` заполнен; strict-валидация проходит; change в архиве.

### 8. Поставка — `ship`

Готово, когда локальная основная ветка совпадает с удалённой, а в дереве нет необъяснённых файлов. Перед этим проверяется, что именно запускает push или merge. Если это выкатка на прод — стоп и вопрос: что выкатится, куда, что будет с данными. Без `--force` и без `reset --hard`. Секреты в коммит не идут.

### 9. Аудит — `spec-audit`

Каждые 5 архивов (`spec-next` сам напоминает) или когда исправления идут, а продукт не работает. Ревью делает агент, который код не писал, в режиме только чтения и с чистым контекстом. На выходе таблица «требование → выполнено, частично или нет → файл:строка» и находки P0–P3. Каждая находка подтверждается по коду, хотя бы один сквозной сценарий проверяется до того места, которое видит пользователь.

## Артефакты change (схема `solo`)

| Файл | Что в нём | Кто заполняет |
|---|---|---|
| `proposal.md` | Why, What Changes, Capabilities, Impact, **Out of Scope** (не пустой), **Depends On** (единственное место зависимостей), **Source** (цитата владельца дословно) | spec-plan |
| `specs/<capability>/spec.md` | Delta: ADDED, MODIFIED, REMOVED Requirements; SHALL/MUST; сценарии WHEN/THEN | spec-plan |
| `verification.md` | **Live Scenario**, **Needs**, **Fallback** — до кода; **Result**, **Not Verified**, **Decisions Without Owner** — после | spec-plan, затем spec-next |
| `tasks.md` | Не больше 10 задач; последняя группа `Acceptance` из двух задач: живой сценарий и validate + archive | spec-plan |
| `design.md` | Только когда без него не обойтись: решения с отвергнутыми альтернативами | по необходимости |

Метки и файлы проекта:

| Файл | Смысл |
|---|---|
| `openspec/changes/<id>/CLAIM` | Change ведёт агент; другой его не берёт |
| `openspec/changes/<id>/WAITING` | Change ждёт внешнего условия; строка в `docs/waiting.md` |
| `docs/waiting.md` | Таблица ожиданий: что, от кого, с какого числа (шаблон — `templates/docs/waiting.md`) |
| `handoff.md` | Передача между сессиями и агентами: пять строк `work-status` и решения |
| `docs/debug-profile.md` | Где что запущено, логи, конфиг, что нельзя трогать без согласия |
| `openspec/analyze.md` | Проверки `spec-analyze`, выведенные из дефектов этого проекта |

## Ворота

| Ворота | Когда | Кто проверяет | Что | При провале |
|---|---|---|---|---|
| G0 | После `project-init` | Ведущий агент | validate, команды из AGENTS.md запускаются, проект поднимается по README | Чинить проект или README |
| G1 | После `spec-plan` | Ведущий агент | validate, analyze, покрытие входа | Дробить или дописывать change |
| G2 | Перед кодом | `spec-analyze` | Нет CRITICAL и HIGH, зависимости в архиве | Править артефакты; change не берётся |
| G3 | После каждого юнита | Ведущий агент, своими командами | Дифф, проверки юнита, `git status` своего дерева | Доработка тем же исполнителем |
| G4 | Перед закрытием | Ведущий агент и независимый ревьюер | Тест падал на прежнем коде; property-тест ловит мутацию; Live Scenario пройден; у ревьюера нет «нет» по требованиям | «Не готово», Not Verified |
| G5 | Закрытие | Ведущий агент | verification.md, strict validate, archive | Не архивировать |
| G6 | Поставка | `ship` | main = origin/main; деплой только с согласия | Остановиться перед деплоем |
| G7 | Каждые 5 архивов | Агент, не писавший код | Требование ↔ код, сквозной сценарий | P0 и P1 чинятся, если исправление разрешено задачей; иначе отчёт владельцу, его можно отдать в `spec-plan` |

## Роли

| Роль | Делает | Не делает |
|---|---|---|
| Владелец | Даёт цель, Source и Замысел; принимает результат; соглашается на деньги, удаление и прод | Не переносит контекст между агентами, не отвечает на технические вопросы по ходу |
| Ведущий агент | Планирует, пишет спеки исполнителям, принимает результат, ведёт артефакты, закрывает change | Не пишет код в оркестрации; не верит отчётам |
| Исполнитель | Делает один юнит в своих файлах и отчитывается в заданной форме | Не трогает чужие файлы, не коммитит, не выдумывает значения |
| Ревьюер | Читает код и спеку с чистым контекстом, только чтение | Не правит то, что нашёл |

Claude Code и Codex равноправны: оба работают по одним правилам (`~/AGENTS.md` = `~/.codex/AGENTS.md` = `~/.claude/CLAUDE.md`) и одним скиллам. Различаются они только инструментом оркестрации.

## Когда что запускать

| Ситуация | Скилл |
|---|---|
| Новая папка или репозиторий без правил | `project-init` |
| «Продолжаем», после паузы или смены агента | `context-resume` |
| «Что выбрать», сравнение технологий или сервисов | `evidence-research` |
| Спорное решение, нужен консенсус нескольких моделей | `model-council` |
| План, список багов, итог обсуждения → в работу | `spec-plan` |
