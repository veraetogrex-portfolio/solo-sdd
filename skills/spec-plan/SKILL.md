# spec-plan: из плана или списка проблем — в очередь маленьких change

Результат — набор change, каждый из которых закрывается за один запуск `/spec-next`. Код не пишется.

## Порядок

1. **Контекст.** Локальные правила проекта, `openspec/config.yaml` (замысел, язык, схема), `openspec list --json`, `openspec list --specs`, `DESIGN.md` проекта, если он есть. Так не появятся дубли уже существующих change и спек.
2. **Единицы.** Раздели вход на единицы. Единица годится, когда выполнены все четыре условия:
   - один результат, который владелец может проверить сам;
   - одна область кода;
   - не больше 10 задач;
   - есть сценарий живой проверки.
   
   Баги группируй по общей причине или области, а не по одному на change.
3. **Порядок и зависимости.** Что должно быть в архиве раньше. Имена — по принятому в проекте образцу (в проекте с номерами продолжай нумерацию).
4. **Сверка с замыслом.** Единица, которая уводит от замысла из конфига, в change не превращается: вынеси её в отчёт отдельной строкой.
5. **Создание.** Для каждой единицы: `openspec new change <имя>`, затем артефакты по порядку, беря инструкцию из `openspec instructions <артефакт> --change <имя>`: proposal → specs → verification → tasks. `design.md` — только если инструкция схемы этого требует.
   - `Source` — дословная цитата владельца, породившая этот change.
   - `Depends On` — имена change из шага 3 или `none`.
   - `Out of Scope` — в том числе соседние единицы этого же плана.
   - `Impact` — в обратных кавычках только пути файлов и каталогов (от корня проекта), которые change создаёт, меняет или удаляет; имена функций, команды, слова и языки — без кавычек. По путям в кавычках диспетчер решает, какие change вести одновременно.
   - Создаваемый change меняет требование с одним именем в одной capability, что другой создаваемый или уже открытый change (`openspec/changes/*/specs/`, кроме `archive`): более поздний получает более ранний в `Depends On`.
   - Change меняет интерфейс, если его результат видит пользователь на экране: страница, панель, виджет, вёрстка, стили. Для такого change:
     - Первый пункт списка What Changes, сразу под заголовком, до всех остальных пунктов — строка `Design Read: <экран> для <аудитории>, <стиль>, ENERGY n / RHYTHM n / MOTION n`. Аудитория — из поля «Аудитория» `DESIGN.md`, стиль — из поля «Характер»; пустое поле или нет `DESIGN.md` — «не указано». Направление задано, только если в `DESIGN.md` есть строка `Dial: ENERGY n / RHYTHM n / MOTION n` с тремя числами от 1 до 3; шаблонные буквы `n` — не задано. Дайлы по словам владельца и по заполненным полям не выводи. Не задано — ENERGY 1 / RHYTHM 1 / MOTION 1 и пометка «черновик без направления» в конце строки.
     - Live Scenario — список «элемент → действие → ожидаемый результат» по каждому элементу управления (кнопка, ссылка, форма, меню), который change создаёт или меняет, плюс ширины 1280 и 390 и каждая тема, которую интерфейс поддерживает. Форма: «пустая форма → отправка → сообщение о незаполненном поле», «верная почта → отправка → сообщение об успехе»; мобильное меню: «меню на 390 → открыть и закрыть → открывается и закрывается».
     - Данные владельца — цифры, отзывы, имена клиентов, логотипы, фото людей: в задачи и сценарии идут только те, что есть в `Source` или файлах проекта. Остальные задача требует как честную заглушку `[нужны данные: <что>]` и называет её дословно, отдельно на каждый вид данных (`[нужны данные: отзывы клиентов]`, а не `[нужны данные: …]`); в `Needs` — список нужного, в `Fallback` — «заглушка остаётся на экране». Change этих данных не ждёт и файла `WAITING` не получает. Правило действует и в режиме `demo`: там выдумываются рабочие данные продукта (сид, эмуляция), но не цифры, отзывы и клиенты владельца.
   - Код change читает чужой вход — файлы, архивы, документы или сетевые данные, путь или содержимое которых приходят во время работы программы (аргумент, запрос, сеть, выбор пользователя), а не лежат в репозитории проекта. Для такого change в `tasks.md` одна задача тестов на враждебный вход. Она относится к требованию, которое вводит чтение этого входа, и называет только пункты, применимые к этому входу. В change уже 10 задач — пункты дописываются в существующую задачу тестов. Применимость решает формат входа, а не задуманный способ разбора: у любого архива есть пути записей, даже если он не распаковывается на диск. Неприменимый пункт не пишется (архив без XML — без пункта про сущности):
     - предел размера и числа записей (ZIP-бомба, степень сжатия);
     - пути записей архива (`..`, абсолютные, ссылки);
     - глубина вложенности;
     - раскрытие сущностей XML;
     - катастрофические регулярные выражения;
     - обрезанный и битый вход;
     - экранирование при вставке в код, HTML или команду.

     Change читает только `AGENTS.md`, конфиги и файлы самого проекта — задача не нужна.
6. **Внешние условия.** Нужен доступ, ключ, человек или платный вызов: запиши в `Needs`. Change целиком из таких условий получает файл `WAITING` и строку в `docs/waiting.md`. Данные владельца под заглушками (шаг 5) `WAITING` не дают.
7. **Проверка.** `openspec validate --all --strict --no-interactive`.
7a. **Сверка.** Скилл `spec-analyze` по каждому созданному change; правки — только в артефактах. Затем повтори шаг 7.
8. **Покрытие.** Каждый пункт входа сопоставь с change. Пункт без change — ошибка: создай change или объясни в отчёте, почему его нет.
9. **Коммит плана.** После ворот G1 (шаги 7, 7a, 8). `git check-ignore -q openspec/changes` нашёл правило — коммита нет, в отчёте строка «план вне git». Иначе `git add -- <папки> && git commit -m "change: <id>, …" -- <папки>`, где `<папки>` — только папки созданных и изменённых change: чужие правки в коммит не попадают. Без этого коммита worktree диспетчера change не увидит.

Больше пяти change: артефакты каждого пишет отдельный исполнитель (в Claude Code — `codex-orchestration`, в Codex — собственные субагенты), ты сверяешь границы и зависимости.

## Багфикс

Вход — один баг или несколько с общей причиной, и причина уже найдена. Change короче обычного, но в той же схеме `solo`, поэтому дальше его ведёт обычный `/spec-next`.

1. **Причина до change.** Нужны воспроизведение (что делается → что ожидалось → что получено) и место в коде, где результат впервые расходится с ожиданием. Нет — сначала `debug-profile`; догадка в proposal не пишется.
2. **proposal.md.** Why — воспроизведение и причина с `файл:строка`. What Changes — только устранение причины. Out of Scope — попутные улучшения, рефакторинг и соседние симптомы, каждый строкой. Source — сообщение владельца о баге дословно. Design Read багфикс не получает.
3. **Спека.** Баг означает, что спека не описывала этот случай или код от неё ушёл. Сценарий бага добавляется в спеку: MODIFIED Requirement (целиком, со всеми прежними сценариями) с новым сценарием или ADDED, если поведение не было описано вовсе. Без delta-спеки багфикс не создаётся: следующий такой же баг спека тоже не поймает.
4. **verification.md.** Live Scenario — шаги воспроизведения: на прежнем коде они дают ошибку, после исправления — ожидаемый результат. В UI-багфиксе — список «элемент → действие → результат» только по затронутым элементам.
5. **tasks.md.** Не больше 5 задач. Первая — тест на сценарий бага, названный по Requirement и падающий на нынешнем коде. Затем исправление причины и при необходимости ещё одна задача; последняя группа — `Acceptance`. Код change читает чужой вход (шаг 5 раздела «Порядок»): эта ещё одна задача — тесты на враждебный вход. Её место нужно под другую работу — пункты дописываются в существующую задачу тестов.
6. **Закрытие.** Шаги 7–9 раздела «Порядок».

Имя — по образцу проекта, со словом `fix`. Если причина затрагивает больше одной области кода, это не багфикс, а обычная единица плана.

## Без вопросов

Не согласовывай разбиение до создания. Создай, покажи отчёт; владелец поправит словами. Неясный пункт входа трактуй по замыслу проекта и отметь трактовку в отчёте.

## Отчёт

```
Создано change: <n>

| № | Change | Результат для владельца | Зависит от | Задач |

Analyze: CRITICAL <n> · HIGH <n> — исправлено <n>
Покрытие: <пунктов входа> из <пунктов входа>; без change: <пункт — причина> | нет
План: коммит <hash> | план вне git
Ждут внешних условий: <change — что нужно> | нет
Мои трактовки: <пункт — как понял> | нет
Дальше: /spec-next
```

## Ошибки

| Ошибка | Исправление |
|---|---|
| Один change на весь план | Дели, пока в каждом не останется 10 задач и один результат |
| Change на каждый баг | Группируй по причине |
| Пересказ просьбы своими словами в `Source` | Только дословная цитата |
| Зависимости в тексте задач | Только в `Depends On` |
| Багфикс без сценария бага в спеке | Сценарий добавляется через MODIFIED или ADDED, иначе баг вернётся |
| Дайлы выведены из слов владельца | Только строка `Dial` с тремя числами, иначе 1/1/1 и пометка «черновик без направления» |
| Выдуманные отзывы или цифры в задачах | Заглушка `[нужны данные: …]` и `Needs` |
| Live Scenario UI-change описан общими словами | Список «элемент → действие → результат», ширины 1280 и 390, каждая тема |
| Change читает чужой вход, а задачи на враждебный вход нет | Одна задача тестов с применимыми пунктами списка из шага 5 |
| Начал писать код | Этот скилл заканчивается на коммите плана |
| Закоммитил всё дерево | В коммите только папки созданных и изменённых change |
