# health: живы ли интеграции проекта

Аргумент (необязательный): что проверить. По умолчанию — всё, от чего зависит проект. Диагностика ничего не меняет. Чинить — по просьбе владельца или через `/debug-profile`.

## Что проверять

1. **Описание проекта.** Если в проекте есть свои проверки, запусти их: `docs/health.md`, раздел о проверке живости в `AGENTS.md`, скрипт `health` в `package.json`, `Makefile` или `scripts/`.
2. **Иначе найди сам.**
   - Имена переменных в `.env` — только имена, без значений: `grep -o '^[A-Za-z_][A-Za-z0-9_]*=' .env`.
   - Сервисы в `docker-compose*.yml`, конфиги, клиенты API в коде.
   - Сопоставь их с типами: база, HTTP API и вебхуки, хранилище файлов, LLM и STT, таблицы и CRM, очереди и планировщики.
3. **Самая дешёвая проверка на каждый.**
   - База — `SELECT 1` и время последней записи в главной таблице.
   - HTTP API — эндпоинт статуса или чтения.
   - Вебхук — метод чтения: профиль, список, информация о приложении.
   - Хранилище — проверка бакета или список из одного объекта.
   - LLM и STT — список моделей. Генерация и распознавание платные: только с согласия, с числом запросов и суммой.
   - Только чтение, ничего не записывай.
4. **Локальные процессы.** `docker compose ps`, занятые порты, последние ошибки в логах, зависшие или необработанные задания.
5. **Провайдер упал.** Посмотри его страницу статуса: идёт ли инцидент.

## Секреты

Ключи передавай в команду через переменные окружения. В выводе маскируй. Значения не печатай и в отчёт не вставляй.
