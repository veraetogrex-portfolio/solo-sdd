# debug-profile: отладка с картой проекта

Общий алгоритм — skill `systematic-debugging` из superpowers. Этот скилл его не заменяет, а даёт ему факты о проекте: где что запущено, откуда берётся конфиг, куда можно смотреть без риска. Без них отладка гадает.

## 1. Профиль проекта

Открой `docs/debug-profile.md`. Нет файла — создай по шаблону, заполнив из репозитория, `.env` (только имена ключей), docker/compose, CI и инструкции деплоя.

```
# Профиль отладки
Режим: demo | prod
Что запускает деплой: <merge в main / push тега / ручной скрипт>
Где работает: <сервер, контейнеры, URL, n8n workflow>
Как узнать задеплоенную версию: <команда>
Конфиг и секреты: <файлы, переменные; где задаются на сервере>
Логи: <команда или путь для каждого этапа>
Данные: <базы, таблицы, что нельзя трогать>
Платные вызовы: <какие модели и API; дешёвая модель для проверки>
Безопасный доступ только на чтение: <команды>
Стоп перед: <действия, требующие согласия>
```

## 2. Диагностика

1. **Воспроизведение.** Тот же сценарий, на котором видна проблема. Запиши, что ожидалось и что получено.
2. **Версия и среда.** Совпадает ли задеплоенный коммит с ожидаемым, подхватил ли сервис новые переменные (`.env` обновлён — контейнер перезапущен?).
3. **Входные данные.** Есть ли они на входе этапа, в том ли формате и периоде.
4. **Локализация.** Пройди цепочку по логам этап за этапом и найди первый, где результат расходится с ожиданием. Логов на этапе нет — сначала добавь их.
5. **Гипотеза.** Одна, проверяемая. До правки выбери наблюдение, которое её подтвердит или опровергнет.
6. **Исправление** в разрешённых границах, затем тот же сценарий из шага 1.
   В проекте с `openspec/` исправление оформляется багфикс-change (`spec-plan`, раздел «Багфикс»): воспроизведение и причина из шагов 1 и 4 идут в его proposal.

Чтение логов, статусов и конфигов делай сам, без вопросов. Перезапуск на проде, изменение данных и платный прогон — только после согласия: назови действие, влияние на данные и сумму.

## 3. Две неудачи подряд

Вторая правка не помогла: остановись. Запиши, какая гипотеза опровергнута и чем. Проверь то, что обычно пропускают: версию деплоя, переменные окружения, права доступа, схему данных, кеш, часовой пояс. Третья правка тем же способом запрещена.

## Отчёт

```
Симптом: <что видит пользователь>
Причина: <этап и почему> | не найдена — <что исключено>
Доказательство: <лог, запрос, вывод команды>
Исправление: <что изменено> | нужно согласие на <действие>
Проверка: <тот же сценарий, где запущен, результат>
Профиль обновлён: да | нет
```

## Ошибки

| Мысль | Что делать |
|---|---|
| «Поправлю ещё раз, должно заработать» | Сначала наблюдение, различающее гипотезы |
| «Локально работает, значит, на проде тоже» | Проверь версию и переменные на сервере |
| «Пользователь не добавил ключ» | Посмотри `.env` и сервер: возможно, уже добавил |
| «Логов нет, буду угадывать» | Добавь логи на этап |
| «Перезапущу контейнер, это быстро» | На проде — только с согласия |
