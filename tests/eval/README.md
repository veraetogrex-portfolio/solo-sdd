# sdd-eval: повтор change и сравнение конфигураций диспетчера

Инструмент `sdd-eval.py` (`global/sdd_eval.py`) повторяет заархивированные change проекта на чистых копиях и сравнивает конфигурации `spec-dispatch` по выполнению, времени и стоимости на одном наборе.

## Порядок работы

0. Запускать из корня репозитория solo-sdd или передавать `--prices <путь>`: `prices.json` не раскладывается по папкам агентов, без него `compare` и `metrics` не найдут цены (`compare` напечатает `файл цен не найден`, время и стоимость будут `н/д`).
1. `sdd-eval.py setup <набор.json> --config <конфигурация.json> --out <E>/a` — копии проекта на базе каждого change (первый родитель коммита-оракула), с нынешними правилами и спеками. Для второй конфигурации: тот же набор, другая конфигурация, `--out <E>/b`.
2. `sdd-eval.py run <E>/a --label a1` — `spec-dispatch` на каждой копии; журнал `<E>/a/runs/a1.json`. Нужно минимум по два прогона на конфигурацию (вторую метку гоните на новых копиях в соседней папке, например `<E>/a2`).
3. `sdd-eval.py metrics <E>/a --label a1` — время, стоимость, роли по журналу сессии; пишет `runs/a1.metrics.json`. `metrics --session <id>` — то же для одной сессии.
4. `sdd-eval.py compare <E> --a a1 a2 --b b1 b2 [--timeout 1800] [--prices …]` — отчёт markdown. Журнал метки ищется в `<E>/runs/`, затем в `<E>/*/runs/`. Код 2 — меньше двух меток у конфигурации или нет журнала; код 3 — у копии нет команды тестов.

## Вопросы владельцу

`claude -p` не показывает окно вопроса, поэтому `run` всегда добавляет `--append-system-prompt`: запрет спрашивать владельца и строки `- <вопрос> → <ответ>` из поля набора `answers` (объект «вопрос → ответ», строки; `setup` пишет его в `.sdd-eval` копии). Ответы рабочего набора: брошенные метки — `Снять и запустить`, спека вместо change — `Не учитывать`, прочие неизвестные зависимости — `Оставить`, режим поставки — `local` (у копий нет remote). Зависимости из `Depends On` разбираются как в `sdd-dispatch-plan.py`; архивные копируются в копию, отсутствующая даёт строку `зависимость не в архиве` при `setup`.

Если в журнале сессии копии есть вызов `AskUserQuestion` или строка «Нужно от вас» с вопросом (не «ничего» и не «нет»), запись копии в журнале прогона получает `question: "вопрос: <текст>"` (до 300 знаков), `run` печатает его после статуса. `compare` ставит `(вопрос)` рядом с исходом ячейки, выводит change в разделе `С вопросом:` и не относит его к перевернувшимся; выполнен он или нет, решают merge и оракул.

Раскладка: `<E>/a/<id>`, `<E>/b/<id>` — копии, `<E>/a/runs/`, `<E>/b/runs/` — журналы.

Файлы: набор `tests/eval/sets/*.json` (проект, не меньше 8 change с коммитом-оракулом, `tests`, `prepare`; набор конкретного проекта называет его и в git не входит, раздел `AGENTS.md` «Рабочая копия»), конфигурация `tests/eval/configs/*.json` (имя и строки раздела «Рабочая копия»), цены `tests/eval/prices.json`, фикстуры `tests/eval/fixtures/`.

## Оракул

Оракул — коммит, в котором change был реализован вместе с тестами. `compare` берёт тестовые файлы оракула, накладывает их на результат прогона (последний коммит основной ветки копии) во временном worktree и запускает команду тестов из строки `Тесты` раздела «Команды» `AGENTS.md` копии. Нет файла, модуля или экспорта: тест-раннер падает, это красный, не пропуск. Выполнен = смёрджен и оракул зелёный. Worktree оракула получает ссылки на игнорируемые результаты `prepare` копии; команда тестов должна быть одной командой без цепочек.

Поле набора `oracle_prepare` (необязательное, строка) выполняется в этом worktree после наложения тестовых файлов и до тестов. Зачем: результаты `prepare`, зависящие от кода change (например нативный помощник, собранный на базе), после merge устарели; `oracle_prepare` пересобирает их. Пересборка идёт через ссылки на папки копии и пишет в копию, это допустимо. Не ноль или таймаут — change не выполнен, среди упавших `oracle_prepare: код N`.

`смёрджен, оракул красный` не значит, что код неверен: тест мог упасть из-за другого текста сообщения или имени. Вердикт выносит ревьюер, не скрипт.

## Метод подсчёта

- Один вызов API — один `message.id`; в журнале у него несколько строк, берётся максимум каждого счётчика.
- Выход модели берётся из `cost-state`: журнал его занижает (прогон 4: Opus 191 485 в журнале против 1 005 077 в `cost-state`). Выход по ролям только журнальный, это нижняя оценка.
- `input_total` включает кэш (ввод, запись и чтение кэша).
- Роли (оркестратор, исполнитель, ревьюер, прочие) и `dispatcher` считаются отдельно.
- Цены из `prices.json`; для сообщения с вводом выше порога `long` берётся тариф `long`. Остаток выхода из `cost-state` сверх журнального считается по верхней ставке модели.
- Время: от первого запуска оркестратора до последнего мёрджа (в `metrics <папка>` — до времени последнего коммита основной ветки копии).
- `возвраты` — сообщения диспетчера (`SendMessage`), `отклонённые` — статусы, не принятые хуком. `смёрджено` — число мёрджей в журнале диспетчера (PR, `land-local`, `git merge`).

## Ограничения

- Копия получает нынешние спеки и документы основной папки (утечка одинакова для конфигураций).
- Проект, где `AGENTS.md` или `openspec/` отслеживаются git, не поддержан: копия выйдет грязной, диспетчер откажется мёрджить (рабочему набору это не мешает, там они игнорируются).
- `MODIFIED` по требованию, которое позже менялось, в копии не проходит `openspec validate --strict` с ошибкой `omits scenario(s)` (один change рабочего набора); оркестратор чинит дельту сам, эта работа одинакова для всех конфигураций и входит в сравнение.
- `run` не задаёт режим разрешений и срок.
- Цены из таблицы claude-api от 2026-10-06; Sonnet 5.5 и Haiku 5.5 скорректированы по факту.
