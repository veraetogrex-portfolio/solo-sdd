# Settings

A project keeps its settings in `solo-sdd/config`: one `key: value` per line, lines starting with `#` are comments, a list value is separated by commas. No file means all defaults. The value in effect is the file value, else the key's item of the `AGENTS.md` section "Delivery" (`Mode:`, `Merge:`, `PR title:`, `Deploy:`, `Owner only:`) or "Working copy" (`Paths:`, `Prepare:`, `After refresh:`, `Shared:`, `Orchestrators:`, `Loopback: needed`, also under "Commands"; a path or number the key refuses is left out and `config list`, `get` and `describe` name it as `AGENTS.md:<line>` on stderr) or the `Mode:` and `Language:` lines of `solo-sdd/project.md` (trimmed, a final dot dropped; a value outside the allowed ones is left out and `config list`, `get` and `describe` name its line on stderr; `config set` never edits the file), else the team default under `mode: team`, else the default.

`solo-sdd config list` prints every key as `<key> <value> <source>` with the source `file`, `AGENTS.md`, `project.md`, `mode` or `default`; `get <key>` prints the value, and `source: <source>` on stderr; `set <key> <value>` and `unset <key>` change only that line and keep comments, order and line endings. `describe [<key>]` explains every key, or the one named: its group, what it changes, its type with the allowed values, the default, the team default and the value in effect with its source; then each checklist pattern and each checklist key set in the file. `list --json` prints the rows of `list` with the same fields as a list of objects. A wrong key or value is refused with exit code 1 and the allowed keys or values, the file unchanged.

`solo-sdd settings` shows the same keys on a full-screen terminal screen and changes them the same way, one edited line per key: a key whose file value overrides a Delivery item of `AGENTS.md` or a line of `solo-sdd/project.md` is marked with that item and its file, picking `delivery.mode: pr` without a CI workflow shows the warning `init` prints, a file changed on disk since the screen read it is not overwritten, and a broken file opens read-only with its line and reason. Its Machine section (`m`) shows the agents laid out, the hooks and the global rules with the layout's source, version and copy counts and the `warn` and `fail` lines of `doctor`, and applies a change by running `solo-sdd uninstall --hooks`, `uninstall --global-rules` and `install --agents …` after it lists them with the folders they change. Its update check switch is saved at once and turns the version check of the home menu and `doctor` off or on ([Update check](cli.md#update-check)); the version line there comes from the cache, without a request.

A model key (`agents.*-model`) takes one model name of ASCII letters, digits, `.`, `-`, `_`, `[` and `]`; a project narrows the models of a role within the machine lists of `~/.claude/hooks/model-policy.json`, never widens them: the `guard` hook refuses a launch on a set orchestrator, review or lookup model outside its list, naming the key and the list, unless the owner set `SOLO_SDD_EXPENSIVE_OK=1`.

A text key (`delivery.pr-title`, `delivery.deploy`, `commit.light-prefix`, `worktree.prepare`, `worktree.after-refresh`) takes one line of printable characters, at most 200, with the ends trimmed, and an empty value when it has no default; its `AGENTS.md` item is read trimmed and as written, without the limit.

A line that is not `key: value`, an unknown key or a wrong value makes the command and the scripts fail with `solo-sdd/config:<line>` and the reason; the hooks take the defaults and write the reason to `~/.claude/hook-state/errors.log`. The `stop` gates and the `CLAIM` creation therefore stay on under a broken file; each gate reads the file of the repository it checks: each edited repository for uncommitted and interface edits, the change's repository for an unarchived change and for `CLAIM`, the session's repository for an open PR. The file is read with the standard library only: the hooks run on `/usr/bin/python3` 3.9.

## Checklists

A checklist names files a person checks by a list before they merge. Two keys per checklist, `<name>` in lowercase letters, digits and `-`; the Checklists section of `solo-sdd settings` (`c`) adds one by its name, paths and file, edits and removes one, and marks a checklist without one of its keys as incomplete and a file that does not exist as missing:

| Key | Value |
|---|---|
| `checklist.<name>.paths` | globs of repository paths, separated by commas (`*` within a name, `**` across folders) |
| `checklist.<name>.file` | a markdown file of `- [ ]` items, from the repository root |

```
checklist.money-safety.paths: billing/**, src/payments/*.py
checklist.money-safety.file: docs/checklists/money-safety.md
```

```
- [ ] Amounts are in minor units, never floats
- [ ] A repeated charge request is idempotent
- [ ] The charge and its refund are logged
```

When a PR's files match the paths (or change the checklist file itself or `solo-sdd/config`), `sdd-pr.py open` and `ship` append to the PR body a section `## Checklist: <name>` with the file's items, unticked; a section already in the body is never rewritten.

`sdd-pr.py merge` and `land` exit with code 8 and `checklist <name>: <n> open items` while an item of the file is not ticked with its own text in the section: a removed, emptied or rewritten section counts its missing items as open, and an extra unticked line is open too. A checklist with one of its two keys, or a file unreadable or without items, stops `open`, `ship` and `merge` with code 1. The settings and the file are read from the main folder, not from the PR.

When every item is ticked, `merge` and `land` still exit with code 8 and `checklist <name>: no approval on <sha>` until the PR has an approving review on its head commit by an account other than the PR author: only the latest review of each account counts (a comment-only review after an approval also needs a fresh approval, stricter than GitHub), a new commit needs a new approval, and reviews that cannot be read count as none.

GitHub does not let the author approve their own PR, so the approval is a person's even when the agent pushes from the author's account; the ticks guide the reviewer, the approval is the gate. A solo project therefore needs a second person (or a second account) to approve a PR that touches a checklist's paths.

`/ship` in a project with `solo-sdd/` merges through `sdd-pr.py open`, `wait` and `merge`, so these gates apply on the ordinary path too, and the `guard` hook refuses `gh pr merge` and a `gh api` call to `pulls/<n>/merge` there. A merge the guard does not read (the GraphQL `mergePullRequest` mutation, a wrapper script, the GitHub web page) still bypasses every `sdd-pr.py` gate; branch protection with required reviews closes that.
